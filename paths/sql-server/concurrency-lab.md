# Opt-in disposable two-session and Query Store lab

SQL Server 2019+ Developer/Express or another authorized training instance; SSMS or sqlcmd with GO support. CREATE DATABASE and database Query Store permissions required. Do not execute on a production/shared application database. The fixed database LN_Disposable_Concurrency_20260927 is dedicated to this fixture. Setup refuses an existing name. Set @OptIn=1 in concurrency-setup.sql only after checking your connection; execute it once. Read all scripts first. These labs were executed on SQL Server 2025 Express build 17.0.1000.7 on 27 September 2026; engine-verification.md records observed results and limits. The schedule below remains a contract to verify on your instance.

Open two new connections A and B to that database. Execute the guard/header first in each tab, then select only the numbered block for the current experiment (including the database/ownership guard directly above it and its GO if present). Do not run the whole session file. Watch A's Step result; start B within A's 15-second pause. If the schedule is missed, wait for both sessions to finish, use ROLLBACK if needed, reset, and retry. Lock timeouts bound waits at 30 seconds; errors must not leave a transaction open. Check SELECT @@TRANCOUNT in both sessions after every experiment: expected 0.

1. Isolation: reset to 100; start A block 1, then B block 1. B's READ UNCOMMITTED sees 150 that will be rolled back. B's lock-based READ COMMITTED waits for A, then sees 100. RCSI is disabled in this fixture: do not generalize the blocking behavior to databases with RCSI enabled. This contrasts dirty reads with committed reads; snapshot isolation is an optional extension, not demonstrated merely by enabling it.
2. Lost update: reset; start A block 2, then B block 2. A reads 100, B reads 100 and writes 120, then A writes stale 110. A asserts final 110, losing B's increment; expected intended sum is 130. Each individual statement remains atomic. A transaction around the same read/write at READ COMMITTED alone does not establish the required read-modify-write policy.
3. Remedy: reset; start A block 3, then B block 3. Atomic UPDATE Value=Value+delta serializes these row increments. B waits, then asserts final 130. Explain why this remedy fits an increment but does not automatically solve arbitrary multi-row business invariants.
4. Deadlock: reset; start A block 4, then B block 4 promptly. A owns row 1 and requests row 2; B owns row 2 and waits for row 1. A's LOW priority makes it victim 1205; its first update rolls back. B commits, asserting both values 120. Record error and transaction count. Timing outside the schedule can produce no deadlock or a timeout; neither is a passed deadlock test. Extension: make both transactions acquire rows in ascending Id order and rerun; use a maximum of three attempts only for 1205, retrying the whole rolled-back unit, not an individual write. Unknown commit outcomes need reconciliation rather than blind retry.

Run concurrency-reset.sql only after both sessions are idle. Never reset during a measurement. Keep evidence: engine version, timestamps, session IDs, raw outputs, assertions and whether you observed blocking/1205.

## Query Store

After the sessions are idle, run query-store-lab.sql in this same dedicated database. Enable actual execution plans in SSMS before running. The skewed fixture contains 10,000 rows, with 100 Category=1 matches. Compare STATISTICS IO/TIME and plans before and after the Category index. The script creates the dedicated LabReadQueryFixture procedure, executes it five times on each side, flushes Query Store, requires at least ten successful captured runtime executions, and returns persisted plan/runtime records filtered by the procedure object_id. Module identity avoids a brittle exact-text match when the engine parameterizes or normalizes SQL; the inspection query cannot count as evidence for the workload. Query Store and optimizer outcomes depend on engine/build/settings; expect captured executions and correct count, do not assert an exact plan count, speedup or operator. Compare execution-count-weighted averages by plan and interval (active intervals can have multiple rows); save actual plans, logical page reads and microsecond durations. A tiny fixture or cached data can hide elapsed-time improvement. Explain scan/seek choice using recorded evidence. The index and LabReadQueryFixture procedure are removed at the end. If interrupted, inspect these two dedicated objects before removing them inside this lab, or use guarded database cleanup and recreate the fixture. Do not overwrite an existing procedure to rerun the experiment.

## Cleanup

Close every connection to the disposable database. Open a master connection, inspect concurrency-cleanup.sql, set its separate @OptIn=1 and execute. Cleanup verifies the exact database and ownership marker and refuses active sessions; it never uses SINGLE_USER WITH ROLLBACK IMMEDIATE or kills sessions. An occupied database makes DROP fail safely. No other database is removed. If setup stopped midway before the ownership table exists, investigate this dedicated database manually rather than weakening the cleanup guard.

## Rounding

Run rounding-lab.sql independently. Expected raw/normalized pairs: 1.004 -> 1.00, 1.005 -> 1.01, both accepted; bad-amount, blank and -1.00 rejected. This is the loader's deliberate decimal scale conversion policy. A strict source-scale policy would require separate validation; accepted rounding is not a malformed-input rejection.
